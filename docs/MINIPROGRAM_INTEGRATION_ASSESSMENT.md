# 易在校园与 RunnerGo 配送接入评估

评估日期：2026-09-14。

代码范围：配送平台 `E:\Runner_delivery`（`d59cbf6`）；小程序 `E:\易谷创新\Gitclone\-`（`4e6062b`）。本次是本地代码评估；没有修改小程序业务代码、登录生产后台、连接生产数据库或部署服务器。

用户确定的目标：同时支持快递代取和商家点餐/购物配送；先接自建 RunnerGo，后续兼容快跑者。下文接口、数据表和新增页面均为建议设计，尚未实现。

## 1. 可用性结论

RunnerGo 可以保留作为配送执行底座。它已经有真实订单状态机、人工派单/改派、骑手履约、角色权限、余额流水及结算幂等。本会话此前完成前后端类型检查、生产构建和 14 项 API 集成测试，并验证本地页面、登录和订单查询。

现有验证只证明平台内部流程；不能证明微信支付、跨系统同步、手机后台通知或生产容量。当前项目不能直接满足“小程序点单 → 自动进入配送平台 → 用户看到履约结果”的要求，也不建议以现状直接上线收费。

两种业务可以共用配送执行流程。商品销售、支付和商家备货归小程序业务后端；配送平台负责取货后的履约及其内部结算。这里的配送单是校内/同城履约任务，不等于顺丰、菜鸟等承运商的电子面单或寄件订单。

## 3. 阻止直接接入的缺口

### P0：没有用户配送业务单及跨系统身份关联

RunnerGo 用户仅有 admin、merchant、rider；配送单必须关联商户，不包含小程序用户、校区、来源业务单号或包裹模型。易在校园用户不能直接拿 JWT 调用依赖 Cookie 的 RunnerGo 页面接口。

小程序统一请求默认识别 `{code: 0, data: ...}` 或 `success: true`，RunnerGo 返回 `{order: ...}`，协议也需要适配。

措施：由易在校园后端鉴权并保存用户业务单；配送平台增加独立服务端接入认证和来源订单唯一关联。所有来源用户、计价、运营商户及配送方选择由后端确认，不能信任前端提交的用户 ID、商户 ID 或金额。用户查单必须校验订单归属，骑手只取得自己的任务。

### P0：支付代码不能原样承接配送收费

本地 `background/routes/pay.js:265` 明确跳过微信平台签名验证，只解密通知资源。`pay.js:301` 金额不匹配时仅记日志，后续仍会将订单写成 paid。支付单更新与支持统计写入也不在同一事务内。

措施：配送支付使用独立业务类型和支付单关联；实现通知原文验签、时间戳检查、平台证书/公钥管理，以及 appid、mchid、业务单、金额、币种核验。金额异常必须拒绝推动订单。支付确认、业务状态更新和待发送配送任务持久化需要事务及唯一约束，正确应对并发重复回调。前端 `wx.requestPayment` 的成功回调不能作为已付款依据。

需要单独实现退款申请、退款结果确认与查单补偿；不能把现有“退商户内部余额”当作退给微信付款用户。原有自愿支持功能仍保持其独立业务含义。

### P0：两套系统之间没有可靠同步

RunnerGo 的 order_events 是本地审计表，尚没有外部回调、签名、持久化发送队列、重试或失败告警。只从支付接口里临时发一个 HTTP 请求，会产生已付款但配送端无单的情况。

措施：小程序后端在数据库事务中保存待发送任务（outbox），提交后由工作进程重试；配送建单使用固定来源业务单号幂等。配送端状态变化与回调任务也在同一事务中保存。接收端按 eventId 去重，并使用每单递增版本防止旧状态覆盖新状态。定时查单补偿解决漏回调或状态间隙。

若请求超时，先用同一来源单号查询/重试，不能立即改用另一配送商重新下单，否则可能出现两个骑手同时接到任务。

### P0：业务收费、运营主体与履约异常尚未定义完整

RunnerGo 按距离计价并扣商户余额。快递代取需要明确校区运营主体，不能把消费者伪装成商家；商品配送需要映射真实店铺。消费者支付金额、商品货款、配送成本、骑手收入与平台收入分别记录。

余额不足会被配送平台拒单，即使消费者已经微信付款也不例外。需要运营余额预警、失败重试、超时处理与退款规则。

现有系统没有找不到包裹、商家缺货、无法送达、退回等完整异常流程。取货前取消与取货后的售后必须分开处理；不能为了退款直接绕过配送状态机。

### P1：运营与运行保障

- 新增骑手或商户目前只创建业务主体，没有完整开通账号、首次设密和重置密码流程。
- 当前骑手列表无实时推送。前台轮询可用于初期试点，但不能保证手机后台或锁屏时接单提醒；需要明确通知渠道和漏单处理。
- 地图为示意图，距离由表单填写。消费者订单应由服务端使用校区/楼栋固定价或可信距离计价；不能由用户填写距离决定费用。
- 包裹取件码需要独立受限字段，按任务授权读取、脱敏展示和生命周期清理，不能塞进可广泛查看的商品说明或日志。
- SQLite 可作为受控单实例试点存储，并非天然不能上线；应先补版本化迁移、备份恢复验证和容量测试。需要多实例或更复杂并发时再规划 MySQL/PostgreSQL 迁移。
- 上线需要 HTTPS、微信合法请求域名、独立环境与账号、进程托管、日志告警。现有 `template/config/api.js` 的 development 与 production 均指向线上域名；联调应建立测试配置，避免测试单进入生产业务。

## 4. 推荐结构

```text
易在校园小程序
  ├─ 快递代取入口 → 驿站 / 包裹 / 收件地址
  └─ 点餐购物入口 → 店铺 / 商品 / 结算 / 收件地址
             ↓
易在校园后端（用户认证、业务订单、支付退款、状态查询）
             ↓ 持久化任务 + 重试
配送适配层 DeliveryProvider
  ├─ RunnerGoProvider（首期实现）
  └─ KeloopProvider（取得官方接口资料后实现）
             ↓
配送平台 → 管理员派单 → 骑手接单 → 取货 → 送达
             ↓ 签名回调 + 查单补偿
易在校园后端更新履约状态 → 小程序订单详情 / 通知
```

客户端一直访问易在校园后端。配送 API 密钥仅保存于后端；浏览器管理后台 Cookie 不用作长期系统间凭据。两个项目的数据库通过 API 协作，不相互直接写表。

快跑者后台账号不是开放 API 凭据。后续兼容仍需取得原厂创建/查询/取消订单、状态回调、认证签名、商户绑定、配额与测试环境资料。适配层应声明支持的能力，不能假设不同供应商状态和取消规则完全一致。

## 5. 双业务首版范围

| 项目 | 快递代取 | 商家点餐/购物 |
| --- | --- | --- |
| 服务类型 | parcel_pickup | merchant_delivery |
| 来源 | 已开通校区的有效驿站 | 已开通配送的店铺 |
| 用户填写/选择 | 驿站、取件信息、包裹规格/数量、收件人、楼栋房间、联系电话 | 商品/SKU、数量、收件地址、联系电话、备注 |
| 服务端校验 | 校区归属、服务时间、包裹限制、服务费 | 实际售价、库存、店铺营业状态、服务范围、配送费 |
| 进入配送的时点 | 支付已确认，或获准的试点免支付规则满足后 | 支付确认 + 商家接受，按约定备货/就绪规则发配送任务 |
| 首版限制建议 | 同一驿站到同一地址；不同取件点分单 | 单店单订单；跨店拆单 |
| 共同履约 | 待派单、待接单、待取货、配送中、已送达、已取消，另有异常处理 | 同左 |

商品部分现有 `price_text`、`total_price_text` 是文本，不可直接作为自动支付金额。必须增加整数分价格、SKU/库存、订单价格快照、库存锁定和释放，并由服务端计算。可复用既有商户和展示页面，不能仅在接龙提交后直接触发收费配送。

## 6. 建议的新增模块和接口

小程序：在首页增加明确的“校园配送”入口，进入页提供“快递代取”和“点餐购物”；快递驿站页保留原有资料入口并增加下单按钮；“我的”增加配送订单列表。新增下单确认、订单列表、订单详情/轨迹、取消/售后页面。

建议独立 `subpackages/delivery` 分包，沿用现有用户认证和校区组件。两个业务用不同表单，共用地址、支付结果和履约详情组件。

易在校园后端建议提供以下新接口（均未实现）：

| 接口 | 责任 |
| --- | --- |
| `POST /api/delivery/quotes` | 校验业务输入并由服务端计算报价，返回有效期及规则版本 |
| `POST /api/delivery/orders` | 按用户和幂等键创建业务单，保存订单价格/地址快照 |
| `GET /api/delivery/orders` | 只返回当前用户的配送业务单 |
| `GET /api/delivery/orders/:id` | 查订单、付款和履约信息，校验归属 |
| `POST /api/delivery/orders/:id/pay` | 返回该业务单的微信支付参数，不接受客户端自行指定实付金额 |
| `POST /api/delivery/orders/:id/cancel` | 根据支付/备货/配送阶段执行取消或转售后，记录取消处理中状态 |
| `POST /api/delivery/providers/:provider/events` | 服务端回调，验签、去重、校验来源订单、处理状态版本 |

配送平台增加 `/api/integrations/v1` 服务端接口族，包括创建、按来源单号查询、取消和事件查询；复用现有领域状态机及结算事务，使用独立服务身份和校区/运营商户权限。

适配器统一 `createDelivery`、`getDelivery`、`cancelDelivery` 和事件标准化能力；报价能力可以由本地业务规则实现，不能假设每家供应商均支持同一种报价接口。

关键新增数据：

- 业务单：业务类型、用户、校区、店铺/驿站、业务状态、支付状态、地址及金额快照。
- 包裹/商品明细：单独保存，不用一段自由文本承担业务结构。
- 配送关联：provider、sourceOrderId、providerOrderId、attempt、履约状态及版本；同一业务单最多一个有效配送任务。
- 运营商户映射：校区/店铺到供应商账户的后端映射。
- 发送任务、接收事件、支付及退款记录：均有唯一键、尝试次数、下次重试时间及错误摘要。

支付状态、商家备货状态与配送状态分开保存。RunnerGo 的 accepted 表示骑手接单，不能直接当成商家已接单；delivered 表示履约送达，也不等于资金已完成全部清算。

## 7. 实施顺序与验收标准

1. 建立独立联调环境和数据迁移；实现来源订单关联、鉴权、幂等建单、查单、取消、事件回传与补偿。
2. 接入快递代取页面及订单详情，以隔离的测试支付/明确免支付测试规则验证端到端流程。
3. 补商家商品交易所需的金额、库存、商家接单/备货和用户支付退款，将其接入同一配送层。
4. 开通真实运营账号、支付及通知，完成真机、异常和恢复测试后，再按校区启用收费试点。
5. 在取得官方资料后增加快跑者适配器，并对其真实接口与状态映射单独验收。

两种业务都属于目标范围；上述顺序用于分段验证，不能把仅代取跑通当作双业务交付完成。

必须通过的验收：

- 两类用户下单均在配送平台出现且业务信息完整；未满足付款/备货规则不应发起配送。
- 用户双击、断网重试、支付回调重复/并发不会产生重复业务单、重复配送或重复资金入账。
- 配送建单成功但响应丢失时能找回原单；配送服务宕机恢复后可补发待处理任务。
- 骑手每次状态变化能回到正确用户的订单；漏回调可补偿、乱序事件不会让状态倒退。
- 余额不足、商家缺货、拒单、骑手改派、取消与取货并发、无法取件/送达都有可追踪处理结果。
- 取消确认和微信退款结果分开跟踪，退款成功前不能展示已退款。
- 普通用户、店铺、骑手之间不能越权查看订单、手机号或取件码；错误签名和重放请求被拒绝。
- 前后台联调、手机真机预览、登录过期、消息提醒及数据库备份恢复均通过；结果记录在发布验收中。

未核实事项：生产微信支付配置及交易情况、快跑者 API 权限、实际营业校区与收费规则、库存数据质量、运营规模及手机通知渠道。本地代码存在不代表生产环境已启用或工作正常。
